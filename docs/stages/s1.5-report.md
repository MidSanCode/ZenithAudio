### 2.1 轮询接线（第二段）

`DegradationMonitor` 把引擎健康喂给策略：注入式 `source`（默认健康桩，故在引擎接入前完全惰性）、~1Hz 定时器、`pollOnce()` 可脱离定时器单独驱动。source 抛异常时**按健康处理**——设备临时读取失败不应静默降级整个会话。真正的引擎读数由 Web 桥或桌面引擎持有者在 `engineHealthSourceProvider` 上 override 即可，无需改本文件。

## 3. 关键设计：为什么警告「粘滞」

计划原文：「**警告不可自动消失——必须用户确认，避免用户误以为已修复**」。因此：

- 警告一经 `evaluate` 触发即 `_warningActive = true`，**之后无论多健康都不清除**；
- `recover()` 把级别逐级降回 `full` 时**才**清警告（用户显式恢复了全部功能）；
- `enableAll()`（「仍要启用」）恢复全部功能但**保留警告**并标记 `userForced`，因为引擎并没有真的变快；
- `userForced` 存在时 `evaluate` **不再降级**——「仍要启用」的全部意义就是让应用停止和用户对着干。测试 `after an override, further bad polls do not re-degrade` 钉住。

---

## 4. 实现中修掉的真实缺陷

1. **`override` 方法名与 `@override` 注解冲突**：Notifier 上定义 `void override()` 会让同文件的 `@override` 注解解析失败（`undefined_annotation`）。改名 `enableAll()`。这是命名坑，不是逻辑坑，但会让整个文件编译不过。

## 5. 已知缺口 / 后续

1. **worklet 驱动**：`lib/engine/web/engine_web.dart` / `worklet_bridge.dart` 与 `AudioWorkletProcessor` JS 骨架**未做**。它依赖 Agent-A 的 `driver/mod.rs` 中 `AudioDriver` trait 已存在（已存在，S1 落地）——但按计划该文件的写权属 Agent-B，且需要真实 WASM 构建流水线。
2. **WASM 构建流水线**：`cargo build --target wasm32-unknown-unknown` + `wasm-bindgen` 的接线未做。核心本身可编译（已由 `cargo check --target wasm32-unknown-unknown` 验证），但 wasm-bindgen 产物与 Web 加载路径未接。
3. **各面板置灰**：`WebDegradationState.isDisabled(feature)` 已就位，但效果面板/发送面板等尚未消费它来置灰。属 UI 接线。
4. **轮询接线**：`updateFromStatus` 需要有人按 ~1Hz 把引擎状态喂进来（Web 端经 worklet postMessage，桌面端本地轮询）。该循环未接。
5. **「降低采样率 / 增大缓冲」的实际动作**：警告条已提供回调入口，但修改采样率/缓冲需要引擎重启路径，未接。

## 6. 增补（2026-10-06）：web 构建阻断项

实际执行 `flutter build web --release` 复核 S1.5 目标时，发现**该目标当前无法编译**——
不是本轮引入，而是既有缺陷。这是 S1.5「Web 端可用」的直接阻断，如实记录：

| 阻断 | 位置 | 说明 |
|---|---|---|
| 🟡 **已修** | `lib/services/cpu_monitor.dart` | 无条件 `import 'dart:ffi'` + `dart:io`，web 端 `dart2js` 直接失败。已拆为条件导出 + `cpu_monitor_{io,web}.dart`，web 桩 `supported=false`/`usage=0`（真实降级信号来自引擎的实时率/xrun，不依赖此项）。 |
| ⬜ 未修 | `lib/providers/project_io.dart` | 多处调用 `ProjectSerializer` 的 `writeProjectDirectory`/`packProjectDirectory`/`readProjectDirectory`，而 web 版序列化器（`project_serializer_web.dart`）**没有这些方法**。 |
| ⬜ 未修 | `lib/providers/sync_provider.dart` | 调用 `unpackProjectArchive`，web 版同样没有。 |
| ⬜ 未修 | `lib/engine/audio_engine_adapter.dart:372` | `disposeService() => _service.dispose()` 在 web 版 `AudioService` 上 `dispose()` 返回 `void` 而非 `Future<void>`，类型不符。 |

**判断**：其余三项需要把 web 序列化器补齐到与 io 版相同的接口面（或把这些调用点用 `kIsWeb` 分支隔离），属较大的独立工作，本轮未做。`cpu_monitor` 的修复是其中唯一既独立又明确的缺陷，已修并保留。

**验证**：修复后 `flutter build web` 仍失败，但失败点已从 `cpu_monitor` 前移到 `project_serializer_web` 的接口缺失——即修复本身有效且已推进一关。

### 6.1 剩余 web 阻断的根因与建议方案（未实施）

根因是**一个类型接口分歧**：`lib/services/project_serializer.dart` 用条件导出在
web 上解析到 `project_serializer_web.dart`，而 `lib/providers/project_io.dart`（两个
平台都编译）调用了 io 版才有的方法，其参数/返回值是 `dart:io` 的 `Directory`——
**在 web 上无法存在同名同签名的桩**。`kIsWeb` 只能保护运行期，编译器仍要解析这些调用。

建议（较大改动，需浏览器实测）：

1. 把 `project_io.dart` 中**依赖 `Directory`/`File` 的持久化逻辑**移入条件文件对
   （`project_io_fs.dart` / `project_io_web.dart`），主文件只保留平台中立的逻辑；
2. 或引入一个平台中立的「工程位置」抽象（io = 目录路径，web = 内存/下载），
   让 `ProjectSerializer` 两边同签名；
3. `sync_provider` 的 `unpackProjectArchive`、web 版 `AudioService.dispose` 的返回类型
   一并按同一抽象处理。

在这三项完成前，**Web 端无法编译**，S1.5「Web 可用」不可声称达成。这是本轮最重要的
如实结论。
